01 Executive summary

Lattice is a single local HTTP/SSE process that speaks three client dialects, routes every request through one immutable core, and delegates each upstream to a plugin. It already behaves like a universal gateway for known providers. It does not yet behave like a universal gateway for unknown providers: adding one still means writing TypeScript, wiring accounts, and editing several hard-coded lists.

What is genuinely solid

  • One core, three ingress dialects: OpenAI Chat, Anthropic Messages, OpenAI Responses (src/core/router.ts).
  • Canonical request/response model with real streaming adapters, SSE event sequence, thinking blocks, tool calls, XML-tool recovery (src/engine/dialect/).
  • Fail-closed circuit breakers with single-owner probe semantics; narrow, deliberate account rotation (src/core/breaker.ts, src/pool/account-pool.ts).
  • Virtual combos with pre-content failover and post-content fail-fast, no model splicing mid-answer (src/plugins/combo.ts).
  • Evidence-first model passports: Ed25519-signed, declared/discovered/measured, no invented context windows (src/core/model-passports.ts).
  • Consentful imports, secret overlay, constant-time auth, nonce-only dashboard CSP, SSRF-safe fetch (src/core/account-import.ts, src/core/secret-store.ts, src/core/safe-fetch.ts).

What is unfinished or misleading

  • "Zero core edits for a new provider" is only true for routing. Accounts, OAuth, admin fallbacks, harness snippets, and alias/combo catalogs are still hard-coded.
  • Manifest metadata (modelPrefixes, models) is decorative in production; the resolver uses cachedModels/listModels().
  • No runtime plugin add/remove/reload. Discovery is a one-time directory scan at startup.
  • bun run why is documented but not implemented; pricing has one row (openai/gpt-4o).
  • GitHub is 31 commits behind the local tree; a large part of the newest plugin work is uncommitted.
  • Auto-generated plugins would inherit undocumented conventions (canonical event names, msg_ IDs, attribution fields, capability declarations) that a doc-scraping LLM cannot infer reliably.

The one-sentence verdict on your idea

The destination is right; Lattice needs a plugin compiler. Lattice already owns the stable runtime, dialects, breaker, pools, passports, ledger. What it lacks is a declarative provider description plus a validation gate that turns "here is a website / GitHub URL" into a manifest, an adapter, credentials, and proof that the generated plugin works. Build that inside Lattice and it becomes universal: one gateway, plugins generated on demand, verified before they ever touch a real request.

Why this is the right shape for "universal"

Everything that must remain trustworthy, protocol fidelity, failure accounting, secret handling, evidence, lives in one immutable core. Everything that changes weekly (a provider's API, headers, auth) lives in a replaceable plugin. That is exactly the seam a generator should target: generate provider-specific code, never touch the core.

The two entrypoints

src/index.ts        source launcher: bun run start, start.ps1, start.bat
bin/lattice.ts      compiled binary launcher: bun run build → lattice.exe
                    extra flags: --env, --log-level

The two paths are near-duplicates. Any new provider that needs account wiring must be added in both (src/index.ts:34-40, bin/lattice.ts:70-76), plus a third time in the admin fallback list (src/admin/admin-router.ts:159-179). That triplication is the main structural tax on adding providers today.

Single-owner breaker rule (newest work)

The router is the only request-level gate and recorder. It calls gateProvider() but deliberately does not call beginAttempt() (router.ts:58-62). The allocator that owns the probe calls beginAttempt() and the release closure calls cancelProbe() (account-pool.ts:167-179); the combo plugin keeps its own target recording with finally { cancelProbe() } (combo.ts:266-268). This prevents a half-open probe from being wedged or double-counted. Plan: docs/superpowers/plans/2026-11-24-router-breaker-single-owner.md.

What counts as a provider-health failure

breaker.ts:38-67: 5xx statuses, TimeoutError, network codes (ECONNRESET, ENOTFOUND, ETIMEDOUT, …), and messages matching network/timeout patterns. Never counted: aborts (by name or code), and all 4xx including 429. Backoff: min(30s, 1s · 2^(n−1)) + 20% jitter; after the wait, allow() becomes true and one probe at a time is admitted.

06 The dialect engine

Three client protocols in, one canonical model in the middle, three protocol-shaped outputs out. This is the part of Lattice that makes it usable by real IDE agents without changing them.

Translation matrix

Client endpointNormalizerWire schemaNotable conversions
POST /v1/chat/completionsnormalizer.ts:40-241types/openai.ts:134-165System messages kept and concatenated; reasoning_content → thinking; tool calls JSON-parsed when possible; images data-URI → base64 part, URL → url part
POST /v1/messagesnormalizer.ts:246-465types/anthropic.ts:150-177Top-level system → systemPrompt + systemContent with cache_control; adjacent same-role messages merged; any→required, tool→function choice; thinking enabled|adaptive → budgetTokens

The canonical contract is CanonicalRequest/CanonicalResponse (types/canonical.ts:198-241,330-338) with content parts for text, image, thinking, redacted_thinking, tool_use and tool_result; nine stream event variants (`:370-379`); nine error categories; usage with an estimated? flag. Every plugin consumes exactly that type.

Important asymmetry

There is a normalizer for each client dialect, but no generic upstream-dialect normalizer. Every provider plugin hand-transforms its own wire payload into canonical. That is why adding a provider costs hundreds of lines of transformation code, and why a generator needs one reusable OpenAI-compatible adapter. Writing that code from scratch each time does not scale.

Outbound and SSE

  • Non-stream serializers (serializer.ts): Chat emits reasoning_content, tool_calls, reasoning/cached token details; Anthropic emits thinking blocks first (with signature), then text, then tool_use, with stop-map tool_calls→tool_use, length→max_tokens; Responses unshifts a message item, emits function_call with call_id, and drops thinking parts in non-stream mode (`:216-277`).
  • Chat SSE (stream-adapter.ts:243-253): initial assistant chunk → deltas → optional usage → finish chunk → [DONE]. On stream_error it emits an error chunk, then [DONE], then returns, the fix that stops SDKs hanging.
  • Anthropic SSE (`:318-560`): strict message_start → content_block_start/delta/stop → message_delta → message_stop; thinking forced to block index 0; parallel tool calls get independent indexed blocks; all blocks force-closed at end. Errors emit event: error without message_stop.
  • Responses SSE (`:611-869`): documented event names and monotonic sequence_number; provider tool event ID preserved as call_id so SDK tool loops echo it; flush order reasoning → text → tool; abort before start still emits created+completed.
  • Stream lifecycle: XML interceptor → withIdleTimeout → tapped generator → dialect serializer. HTTP status stays 200 for stream errors; the error travels in-band.

XML tool-call interceptor, the sharpest piece of engineering here

Some models stream tool calls as plain text markup (<tool_call>, <invoke name=…>, <function_call>). Clients expect structured tool_calls. The old regex parser broke on chunk boundaries, heredocs, entities and oversized junk. HEAD commit 054059c replaced it with a character scanner:

  • tokenize() (`:63-130`) emits text|open|close tokens, handles quoted/unquoted attributes and legacy <function=name>; a bare < is text.
  • parseCalls() (`:139-259`) resolves nesting, <parameters> JSON and <parameter name=…> values, four markup shapes, JSON-or-string argument values.
  • decodeEntities() (`:13-54`) handles named entities and numeric decimal/hex up to 0x10ffff, 16-char cap, single pass.
  • Budget: MAX_XML_BUFFER_BYTES = 4096, measured in UTF-8 bytes with code-point-safe clipping (`:282-297`); over-budget with a closing tag emits only decoded inner payload, never markup; malformed advertised XML is dropped, never echoed (`:400-409`).
  • Success emits call_lat_<12 hex> IDs, tool_call_start/delta/stop triples, and rewrites stream_end.stopReason from stop to tool_calls.

Reverting that commit in an adversarial audit produced raw <function_call> leaking into content, the fix is real. Coverage: tests/unit/p1-7-xml-stream-parser.test.ts.

Error normalization

GatewayError (types/errors.ts:74-127) redacts its message in the constructor, derives a category from status, and converts retry-after units. Serializers map status to dialect-specific types: 400 invalid_request_error, 401 authentication_error, 403 permission_denied_error/permission_error, 429 rate_limit_error with retry-after, 503 overloaded_error on Anthropic, 504 gateway_timeout, and a generic api_error/internal_error otherwise. Global handler picks the dialect from the path (server.ts:161-190).

Decentralized classification

Plugins classify upstream errors themselves and often throw new GatewayError(status, String(status), 'Upstream error: …'), so the wire error.code is frequently a numeric string and the text is provider-specific. Normalization happens at serialization. A generated plugin must implement classifyError itself.

Virtual combos

LatticeComboPlugin (src/plugins/combo.ts) is a virtual plugin. It resolves virtual model IDs like lattice/code-flagship, consults signed passports for context windows (never guesses from model names), pre-checks quota, and tries up to MAX_STREAM_TARGET_SWITCHES = 4 targets with per-tier failure caps. It buffers until the first content event before committing, stream_start alone does not count, so "connected then died" remains retryable. After content, a failure emits stream_error; the original model stays. Combos are data definitions (docs/combo-policies.md:3-5, src/pool/combo-policies/fast-free.json), which is the right shape for generated providers to join.

Evidence-first model passports

Record

Schema v1 (model-passports.ts:32-46): id, providerId, generatedAt, claims, availability, digest, Ed25519 signature + keyId + publicKey. Key at <dataDir>/model-passport-key.json, mode 0600. Payload is canonical stable-stringified before hashing/signing (`:77-115`).

Evidence ladder

declared (plugin descriptor) → discovered (provider catalogue) → measured (explicit probe or passive traffic). Catalogue refresh never downgrades a measured claim (`:251-265`). Duplicate measured observations are deduplicated so hot routes do not rewrite the file.

Passive learning (passport-observation.ts) upgrades claims from real tool calls, thinking blocks, accepted streams and context-overflow errors, no extra provider call. Explicit probing is opt-in: POST /api/models/probe runs one token with a 30 s deadline and records availability only; it may consume provider quota. A signature proves record integrity. Provider claims stay unverified. Unknown values stay absent.

Cost honesty

Prompt tokens come from real BPE (gpt-tokenizer). Completion tokens use upstream usage only when usage.estimated !== true; otherwise they are counted from accumulated text and the ledger row is stamped estimated:true. costUsd returns null for estimated usage, free tiers and unknown prices (pricing.ts:35-46). The price table currently has one row (openai/gpt-4o, pricing-data.json), so almost every dashboard cost field is null.

Residual gaps worth fixing before expanding trust

  • Generic 500 responses in server.ts:184-189 still bypass the new redactor.
  • DNS names that resolve privately after URL validation are explicitly out of scope, DNS rebinding is not handled (config.ts:3-5).
  • EventSource('/api/logs/stream') cannot set headers, so the live log stream returns 401 when admin auth is on; no test covers it.
  • CI workflow triggers on main, but the repository branch is master, CI may never have run on the real branch.
  • .gitignore lists exact data filenames; backup and rotated ledger files can be committed by accident. README.md claims MIT but no LICENSE file exists.
  • Hardcoded reverse-engineered constants have no config override: Cline WorkOS client ID/versions (cline.ts:26-35), OpenCode CLI fingerprint and session algorithm (opencode.ts:60-196), DeepSeek PoW placeholder (deepseek.ts:304-307), Nous client_id:'hermes-cli'.

Design constraint for auto-onboarding: every new trust surface you add (URL fetch, generated code, captured keys) must land inside these existing boundaries. In particular, a provider URL fetch must reuse safeFetch and reject redirect-to-private; generated code must not be imported in-process without isolation or review.

09 Observability, conformance and tests

Ledger → receipt → dashboard

Every request appends a compact NDJSON row (requestId, timestamp, method, path, provider, accountId, model, status, latency, tokens, estimated?). Retention 7 days; rotation at 10 MiB or 24 h; 10,000-row recent cache; O(1) dashboard queries via per-provider cumulative timelines and binary search; null-prototype maps so a provider literally named __proto__ stays data. A 500-entry ring feeds the SSE log stream. buildReceipt() can render any request ID or prefix, but no CLI/route calls it yet, so bun run why … remains documentation only.

Dashboard inventory

Overview/KPIs, Free Models Explorer (live per enabled provider), Harness Setup (7 clients), hidden Token Telemetry, Usage analytics, Quota Tracker, Credential Pools, Virtual Combos with 3-step wizard, Provider Plugins toggle, Live Ingress Stream. Sidebar actions cover credentials, combo wizard and "simulate telemetry", the last one calls an endpoint that does not exist (/api/telemetry/simulate). 10 The plugin system (the seam that matters most)

This is where your idea lives or dies. Lattice already has a plugin contract, a manifest, a loader, lifecycle hooks and one migrated plugin. What it does not have is a way to produce a correct plugin from documentation, or to register one without a restart.

The contract, ProviderPlugin

Defined at src/core/types/plugin.ts:118-149. Required members are marked; everything else is optional.

interface ProviderPlugin {
  readonly id: string;                    // REQUIRED
  readonly displayName: string;           // REQUIRED
  readonly defaultBaseUrl: string;        // REQUIRED
  listModels(account?: StoredAccount): Promise<ModelDescriptor[]>;  // REQUIRED
  execute(req: CanonicalRequest, signal?: AbortSignal): Promise<CanonicalResponse>;  // REQUIRED
  executeStream(req: CanonicalRequest, signal?: AbortSignal): Promise<AsyncIterable<CanonicalStreamEvent>>; // REQUIRED

  description?, supportedAuthTypes?, capabilities?, cachedModels?
  initialize?(ctx: { dataDir: string; logger: unknown }): Promise<void>
  shutdown?(): Promise<void>
  healthCheck?(account?): Promise<HealthCheckResult>
  refreshAuth?(account): Promise<StoredAccount>
  classifyError?(error, statusCode?, body?, account?): ErrorClassificationResult
}

StoredAccount (`:20-48`) carries accessToken, refreshToken, apiKey, cookies, organizationId, baseUrl, plus ~15 runtime fields (status, cooldown, quota, token/request counters). ErrorClassificationResult (`:89-103`) has 9 categories, isRetryable, optional cooldownDurationMs and a message. ProviderCapabilities (`:109-116`) has exactly three flags: responseFormat, samplingFields, cacheControl, and only the first two are enforced (capabilities.ts:19-35). Type re-export gap: types/index.ts does not export plugin-manifest.ts.

The manifest as data

src/core/types/plugin-manifest.ts:15-32 (hand-written interface, no Zod validation):

interface PluginManifest {
  id: string; displayName: string; description?: string; defaultBaseUrl?: string;
  modelPrefixes?: string[];              // "kilo/" style, decorative in production
  models?: Array<string | ModelDescriptor>;
  capabilities?: ProviderCapabilities;
  supportedAuthTypes?: AuthType[];       // oauth | cookie_pool | api_key | anonymous
  configSchema?: Record<string, PluginConfigField>;  // type, required, env, default
  adapter: string;                       // module path relative to manifest
  factory?: string;                      // default: createPlugin
  enabled?: boolean;
  lifecycle?: { hooks?: Array<'initialize' | 'shutdown'> };
}

The only production manifest, src/plugins/manifests/opencode.json, declares id, displayName, base URL, prefixes, three models, two capabilities, two auth types, adapter ../adapters/opencode.ts and no hooks. The adapter is a 7-line factory (src/plugins/adapters/opencode.ts) returning new OpenCodeProviderPlugin(config.baseUrl). The minimal test fixture is tests/fixtures/throwaway-provider/manifest.json.

What the loader validates

src/plugins/registry.ts:50-79, in order: read top-level *.json from one directory, sorted; JSON.parse unguarded; check only that id, displayName, adapter are truthy; resolve + dynamic-import the adapter module; look up factory ?? 'createPlugin' and require a function; await it with env-resolved config; require the result to be truthy with matching id; require every declared hook to exist as a function; register with enabled !== false.

Validation is theatrical

A plugin missing execute() registers cleanly and crashes on first request. A misspelled capabilites is silently ignored. A bad manifest aborts startup. resolveConfig coerces numbers with bare Number() (no NaN check) and booleans with value === true || value === 'true'. Discovery is one non-recursive directory scan at startup, no hot registration, no unregister, no persistence of setEnabled.

Lifecycle

src/core/plugin-lifecycle.ts: initializePlugins awaits hooks sequentially in registration order, gated by each manifest's declared hooks (`:16-25`); shutdownPlugins runs in reverse (`:28-36`). Startup call at src/index.ts:72 and bin/lattice.ts:93; shutdown on SIGINT/SIGTERM. No try/catch: one throwing hook aborts startup or shutdown. Both loops iterate getEnabled(), so a plugin disabled after startup will not get shutdown(). "Hot reload" in this codebase means accounts only (admin-router.ts:224-240), never plugin code.

  3. Implement the six required members plus whichever hooks the manifest declares.
  4. Hand-write upstream auth, URL resolution, body/header mapping, canonical response transform, SSE event sequence, error classification, cooldown/rotation, account acquisition and msg_ ID rewriting.

Routing itself needs no core edit. A complete integration needs five or six. Why Lattice should own onboarding

  • It already owns the trust primitives. Secret store, redaction, SSRF guard, nonce CSP, token auth, consentful import, audit ledger, an external agent has to reinvent or bypass all of them.
  • It already owns the verification primitives. Conformance runner, passports with evidence levels, explicit probes, breakers, receipts, the generated plugin can be scored before it is trusted.
  • It already owns the integration surface. Manifest loader, adapter factory, lifecycle hooks, combo-as-data, harness manager. The seam exists; only the producer is missing.
  • Feedback loop is local and cheap. A gateway can send a test request through its own dialect stack and compare canonical events to the conformance expectations. An outside agent cannot see that without reimplementing the gateway.

Design rule to hold onto

Generate data first, code last. Most new providers are OpenAI-compatible. A manifest with endpoint, auth, headers, model mapping and capability flags should be enough, no generated TypeScript at all. Only fall back to a narrow, reviewed adapter template when the wire shape truly differs. This keeps the core immutable and makes the generated artifact auditable.

D. Adapter templates over generated code

Tier 1, declarative (preferred)

One generic adapters/openai-compatible.ts driven by wire.protocol, defaultBaseUrl, headers, prefix strip, model map and capability flags. Covers most new providers with zero generated TypeScript. Implement once; reuse forever.

Tier 2, templated custom

A narrow adapters/generated-template.ts with fixed slots for auth, URL, request transform, response transform and SSE mapping. The generator fills slots from the provider profile. Output is deterministic, diffable and reviewable, never arbitrary code.

Process isolation (LATTICE_GATEWAY_INDEPENDENT_ENGINEERING_AUDIT.html §20.3) is only needed if you ever allow genuinely untrusted adapter code. Tier 1/2 avoid that class of risk entirely. If isolation is added later, keep the in-process path for first-party plugins.

  4. Passport: observe descriptor claims as declared/discovered; let real traffic upgrade to measured; never invent context windows or costs.
  5. Confirm: show the scorecard in the dashboard, require an explicit user click to enable. Log the decision to the ledger with the source digest.

Surface a single "Verification" panel in dashboard-ui.ts next to the Provider Plugins table (`:2078-2149`), including source URL, digest, each check's result, and a rollback button.

13 Risks, anti-goals and failure modes

The risk that dominates all others: trusting generated code

A generated plugin runs in-process with access to the secret store, filesystem and network. An LLM reading a provider's docs is reading untrusted input: a malicious or compromised docs page can inject instructions ("also send every key to …"). Mitigations: never execute arbitrary generated code; prefer declarative adapters; treat fetched docs as data, never as instructions; hash and show the source digest; require explicit user confirmation; keep all outbound fetch through the SSRF guard; run verification on a mock upstream before any live request; log everything to the ledger.

Explicit anti-goals from the project's own spec

  • No signed lies: a valid signature must never be presented as proof a provider's claim is true.
  • No hidden account harvesting: imports and credential capture are consentful, previewed, redacted and single-use.
  • No affinity trapping a request on a dead account; no handoff after content has been emitted.
  • No startup calls or test-time provider calls; no simulated telemetry or decorative metrics.
  • No "hundreds of decorative providers", no model switching per message, no claiming a conformance badge without an executable runner, no committing binaries or credential stores.
  • No remote centrally signed catalogue, that would transfer trust and add a remote dependency.

Adoption rule: treat every generated plugin as untrusted until it passes the verification gate, and re-verify on source digest change. The gateway's credibility rests on its honesty machinery; an auto-onboarding feature that skips it would undo months of deliberate work.

Glossary

Canonical request/response
Internal protocol-neutral shape. All three client dialects normalize into it and all plugins consume it.
Plugin
Provider-specific implementation of ProviderPlugin. Combos are a plugin that delegates to other plugins.
Adapter
Thin factory module that a manifest imports to construct a plugin from config.
Combo
Virtual model with ordered failover targets; a data definition.
Passport
Ed25519-signed, evidence-graded record of model claims. A signature proves integrity. It says nothing about truth.
Breaker
Provider health gate: closed → open → half-open with one probe at a time.
Affinity
Hashed session key pinning a conversation to a target/account in memory only.
Harness
A coding client (Claude Code, Cursor, etc.) plus the config that points it at Lattice.
Safe rotation
Switching accounts only on provably unprocessed requests (429/401/403); fail fast otherwise.

01

Executive assessment

Lattice Gateway is a serious piece of engineering that solves a real, narrow problem well: it gives one operator a single local endpoint that speaks the three dialects coding agents use, and spreads their requests across many free or keyless upstream accounts. It is not, yet, a production-grade general-purpose LLM gateway.

The strongest parts are not the ones the README leads with. They are the canonical dialect layer, which is a genuine internal representation rather than a pile of conditional translations; the failover engine's decision to switch targets only before content reaches the client, which avoids duplicated tool calls; and a deliberate, tested refusal to fabricate telemetry. The model-passport system separates declared, discovered and measured claims and signs records with Ed25519, while being explicit that a signature proves integrity, not truth. That is unusually mature thinking for a project of this size.

The gaps are structural, not cosmetic. Routing is not intelligent in any adaptive sense: account selection is effectively "first active account", a real round-robin implementation exists but has no callers, and the passport system's health and latency observations are never consumed by any selection path. Persistence writes the primary state file non-atomically and silently discards corrupt data on load, while all runtime quota and cooldown state lives only in memory. The OpenAI Responses stream emits event names and delta shapes that do not match the documented protocol, discards provider tool-call IDs, and drops reasoning content. Errors are frequently surfaced as successful completions with HTTP 200. There is no CI configuration at all.

None of this makes the project unserious. It makes it a strong prototype with a clear identity and a set of well-understood engineering debts. The audit found confirmed defects in credential handling, registry wiring, persistence, cancellation, and dialect fidelity; it also found hardening work that is recent, deliberate, and in several places better than what comparable small gateways ship.

What is real

Canonical dialect conversion, real HTTP test harness, 676 passing tests, Ed25519 passports with evidence classes, consentful two-step import, bounded hashed session affinity, pre-content failover, honest-usage guardrails.

What is claimed but thin

"Everything is a plugin" (routing hardcodes prefixes), "intelligent routing" (static ordered lists), "capability verification" (only context window is read), "unified cost telemetry" (one illustrative constant).

What is missing

Circuit breakers, backoff, idempotency, migrations, backup, retention, per-model pricing, CI, multi-tenancy, distributed state, deep conformance, structured-output and multimodal fidelity.

What would change its class

Atomic versioned persistence, a single routing decision engine fed by health and cost signals, protocol-accurate streaming, cancellation that actually aborts upstream work, and enforced security boundaries with CI.

Evidence boundary

Every conclusion in this report is tied to a file and line number in commit b094a19, to an executed command, or to an external source named in the appendix. Findings are labelled confirmed (reproducible from source or execution), limitation (real but by design or bounded), risk (plausible failure path not reproduced), or missing (no implementation exists). 02

Project identity and purpose

Lattice Gateway is a single-process, loopback-oriented HTTP service written in TypeScript and run on Bun. It presents OpenAI Chat Completions, Anthropic Messages and OpenAI Responses endpoints on one port, translates all three into an internal canonical shape, and forwards each request to one of six upstream adapters or a virtual "combo" pipeline. Its operator audience is a single developer running coding agents locally against accounts they already own — frequently free-tier, keyless, or session-based accounts that were previously exposed through separate daemons on different ports.

The stated philosophy is "everything is a plugin": an immutable core plus self-contained provider adapters. The code supports part of that claim. ProviderPlugin defines a real seam — listModels, execute, executeStream are implemented by every adapter, with optional lifecycle hooks that nobody implements (src/core/types/plugin.ts:109–137). Registration is a registry with enable/disable state (src/plugins/registry.ts:4–45). But provider selection does not flow through the registry alone. Two independent resolvers exist, and both hardcode provider identity: resolveTargetProviderId lists freellmapi/, kilo/, cline/, nous/, deepseek/, opencode/ and lattice/ as literal prefixes plus substring heuristics (src/utils/model-resolver.ts:5–48), while the router repeats a different prefix/catalog resolution algorithm (src/core/router.ts:177–242). Adding a provider means editing the resolver, the two entrypoints, and likely the admin catalogue. The plugin boundary is a genuine abstraction for execution; it is not yet an abstraction for discovery.

The product's real differentiator is therefore not extensibility but aggregation: it turns a messy set of upstream account types — OAuth, WorkOS, cookies, anonymous keyless access — into one stable dialect surface with cooldown handling and ordered fallback. That is a useful thing to build, and the codebase takes it seriously rather than treating it as a thin proxy.

There is a visible self-correction culture. tests/unit/honesty-guard.test.ts asserts that seeded counters, multipliers, fabricated log rows and claims of proxy rotation or uTLS are absent from the source and README. A design specification (docs/superpowers/specs/2026-11-18-lattice-phase-c-design.md) explicitly names "a signed lie" as an anti-goal and states that signatures prove record integrity, not model truth. These are not generic quality statements; they are responses to specific failure modes the project has already had, and they are encoded as tests.

Architecture overview

A request enters through a Hono application created by createServer. Four middleware layers run before any route: request ID propagation, a browser-origin guard, CORS, a body-size limiter, and bearer authentication. The router then normalizes the request into CanonicalRequest, resolves a model string to a plugin, measures prompt tokens locally, and calls either execute or executeStream. Provider adapters own account selection and upstream HTTP; the combo plugin owns multi-target failover. Responses are serialized back into the client's dialect, and streaming responses pass through an XML tool interceptor and timeout wrapper before an SSE adapter writes wire events.

Two architectural properties are worth stating plainly. First, the router never chooses an account and never expands a combo; it resolves a model string to a plugin and delegates. Account selection lives inside each adapter, and failover logic lives in the combo adapter. This keeps the router small but duplicates account-selection logic across four large plugins. Second, dialect detection is purely path-based: /v1/messages means Anthropic, /v1/responses means Responses, everything else means OpenAI. There is no content sniffing, which is correct for a gateway but means error shapes depend on the URL the client happened to use (src/core/server.ts:167–196).

The admin surface is mounted into the same Hono application and shares the middleware chain, with a stricter token class for /api/* and /admin/*. The dashboard shell at /admin is intentionally public; its data APIs are not. That separation is sound, though the dashboard's token entry is manual and stored in sessionStorage, which is an appropriate choice for a local tool (src/admin/dashboard-ui.ts:2388–2398).

05

End-to-end request lifecycle

The same eleven steps run for all three dialects; only the normalizer, serializer and SSE adapter differ. The sequence below follows a successful streaming request through the system, because streaming is where the interesting behavior lives.

  1. Transport guards. A request ID is assigned or accepted from x-request-id; a foreign Origin is rejected unless explicitly allowlisted or loopback; CORS headers are applied; bodies are limited to 10 MB by declared length or by draining and reattaching a chunked stream; a bearer token is required except on a small public-path set (src/core/server.ts:55–164).
  2. Parsing. The handler calls c.req.json(); invalid JSON becomes a 400 in the client's dialect. There is no JSON Schema validation of the request beyond per-dialect Zod schemas inside the normalizers.
  3. Normalization. The dialect-specific normalizer produces a CanonicalRequest. Session identity is derived separately from the x-lattice-session header or metadata keys, hashed to ses_…, and attached as an affinity hint.
  4. Model resolution. Aliases such as claude-sonnet-4-6 map to lattice/code-flagship. The router then checks provider prefix, plugin ID, and a 60-second catalog cache. Unknown models return 404. A special case routes every model to the only plugin when exactly one is registered, without validation (src/core/router.ts:189–193).
  5. Edge token counting. countPromptTokens uses the gpt-tokenizer BPE synchronously on every request, including images at a flat 1,000 tokens each. This value is the fallback usage when the upstream does not report it.
  6. Execution. Non-streaming calls are wrapped in withRequestDeadline (30 minutes by default). Streaming calls obtain an async iterable from executeStream.
  7. Account and upstream. The selected plugin picks an account — in practice the first active one, preferring a session-pinned ID — resolves credentials through the secret store for imported accounts, and sends the upstream request. 401 and 429 rotate accounts with cooldown handling; ambiguous network failures fail fast by design.
  8. Combo handling. If the resolved plugin is lattice, the combo engine walks its ordered targets, applies context-window and quota guards, and buffers stream events until the first content-bearing event before committing to a target.
  9. Event processing. Every stream event updates passport observations. The XML interceptor may convert text deltas that look like XML tool calls into canonical tool events. An idle/request timeout wrapper can emit a synthetic error event.
  10. Serialization. A dialect SSE adapter converts canonical events to wire events, adds keepalive comments, and emits a terminal event. Usage is recorded and a structured log row is appended in the generator's finally block.
  11. Observation. The router broadcasts a redacted log record to the dashboard and appends it to the NDJSON ledger. No prompts, completions, headers or credentials are recorded.
06

Component-by-component technical analysis

6.1 Server and middleware

createServer builds a Hono app and mounts middleware in an order that matters. The browser-origin guard is a genuine defense: a loopback service is still reachable from a page the operator visits, so requiring an explicit allowlisted or loopback Origin closes a class of DNS-rebinding and drive-by requests (src/core/server.ts:19–29, 67–78). CORS defaults to two explicit loopback origins. The body limiter drains chunked bodies and reattaches a buffered Request, which is correct but means a 10 MB request is fully resident in memory before routing.

Authentication compares tokens with a plain string inequality (src/core/server.ts:156). With 192-bit random tokens this is not a practical remote timing attack, but it is not constant-time either. More consequential: both tokens are printed to stdout at startup in the source entrypoint (src/index.ts:109–110) and the binary entrypoint (bin/lattice.ts:92), so terminal scrollback, screen sharing and process log capture can disclose them. The token file itself is generated with randomBytes(24), written with mode 0600 and re-chmodded where supported (src/core/auth-tokens.ts:30–39) — solid for a local tool.

6.2 Router

The router is 687 lines of which roughly 440 are three near-identical endpoint handlers. Each repeats normalization, resolution, token counting, a non-streaming branch, a stream-tapping generator, SSE construction and response headers. The duplication is not merely aesthetic: the same fix has to be applied three times, and the three copies already differ in small ways (for example, which dialect is considered in the 404 handler). A single dialect-parameterized handler would remove most of this surface without changing behavior.

The router's account of its own responsibilities is honest: it records aggregate provider usage but does not choose accounts. That means quota attribution is based on "the active account with the newest lastUsedAt" in the pool (src/pool/account-pool.ts:360–373) rather than the account the plugin actually used, which is wrong under concurrency. It also means a client abort can be logged as a successful request: the stream-tapping generator's finally block records usage and a 200 status whenever no stream_error was observed, and client abort returns silently from the timeout wrapper (src/core/router.ts:348–371, src/utils/idle-timeout.ts:91–93).

6.3 Dialect engine

The canonical model is the project's best architectural decision. It defines content parts for text, image, thinking, redacted thinking, tool use and tool results, a request type carrying tools, tool choice, thinking config, reasoning effort, stream options and affinity, and a nine-variant stream-event union (src/core/types/canonical.ts:23–336). This is a real intermediate representation: the three ingress normalizers and three egress serializers are independent of each other and of the plugins.

Happy-path behavior is covered and mostly correct. OpenAI Chat tool-call deltas use the canonical index properly; Anthropic thinking, text and tool blocks are assembled into a state machine; the Responses JSON serializer produces a coherent response object. The weaknesses are in the long tail, discussed in section 10: request fields accepted but dropped, error stop reasons collapsed into success, Responses streaming event names that do not match the public protocol, and tool-call IDs replaced with locally generated ones.

6.4 XML tool interceptor

This component solves a real problem for open-weight models that emit tool calls as XML inside ordinary text deltas. It buffers text, recognizes four shapes, emits canonical tool events with a generated ID, and falls back to plain text when parsing fails. Its limitation is structural: parsing is regex-only. There is no entity decoding, attributes on <tool_call> break the match, non-greedy inner patterns fail on nested content, and two recognized prefixes — <function_call> and <function_calls> — are listed as trigger prefixes but have no corresponding parser, so they are eventually flushed as raw text (src/engine/dialect/xml-tool-interceptor.ts:126–131, 189–239). The 4 KB buffer bound is measured in UTF-16 code units rather than bytes. These are contained risks for the models it was built for, but they are the exact edge cases coding agents hit when a model emits malformed tool XML.

6.5 Account pool and credentials

The pool has a well-thought-out state model: active, cooldown, suspended, expired, invalid; Retry-After parsing; a four-hour threshold that converts a long rate limit into zero remaining quota; reset times; and an error count that invalidates an account after five failures. What it lacks is selection intelligence and concurrency control. getNextRotatedAccount implements per-provider round-robin but has no callers in src/; adapters instead pick active[0] (src/plugins/kilo.ts:400–409). Account objects are mutated in place, with no reservations or locks, so concurrent requests can collide on the same account.

Credential resolution is cleanly separated: imported accounts carry an opaque acc_import_ ID and no secret in the store; the resolver fetches secrets by ID from the secret store for those accounts only (src/core/credential-resolver.ts). That design prevents the main JSON store from re-absorbing credentials after import, which is a meaningful integrity property.

6.6 Model passports and observation

Passports are more careful than most capability systems. Each record carries claims with a source of declared, discovered or measured, an observation time, an evidence string, a canonical-content digest, a signer key ID, the public key and an Ed25519 signature. Verification checks the digest, the key-ID/public-key binding and the signature; load rejects invalid or foreign records; measured claims are preserved across catalogue observations; and unknown values are absent rather than defaulted (src/core/model-passports.ts:77–241). The one routing consumer is context-window selection in the combo engine, which requires verification before trusting the claim (src/plugins/combo.ts:62–75).

Two gaps undermine the system's potential. observe() rebuilds a passport from a descriptor and copies measured claims but not the current availability field, so a later catalogue refresh wipes an explicit probe's result (src/core/model-passports.ts:250–263). More broadly, availability.healthy and latencyMs are written but never read by the router, combos or account selection. The "capability learning" loop therefore improves the dashboard, not routing.

6.7 Ledger, telemetry and admin

The ledger records only numeric and routing fields and is redacted by omission — no prompts, completions, headers or credentials — which is the right design and is guarded by tests. Its implementation is a synchronous appendFileSync per request and a full-file read and JSON parse for every metrics query, with no rotation or retention. The admin router exposes roughly 43 routes covering accounts, OAuth, import, combos, plugins, passports, probes, harness setup, logs and telemetry. All are behind the admin token, and the dashboard obtains that token from the operator rather than embedding it. The harness manager writes realistic provider configuration into client settings, including a fixed placeholder API key sk-lattice-master in generated configs (src/admin/harness-manager.ts:375–618); this is a local placeholder, not a server credential, but it should be derived from the configured gateway token to avoid confusion and to work when the token is rotated.

High Hardcoded fallback credential. FREELLMAPI_DEFAULT_KEY is a literal API key in source, used as the account credential and as a final fallback in request headers (src/plugins/freellmapi.ts:19–22, 43–55, 77–86). The upstream is a local service on port 31415, so this is not a cloud secret, but it is a shared credential committed to source. It should be required from configuration and fail closed when absent.

High Fabricated challenge solution in DeepSeek. solveChallenge() posts a literal solution: 'solved_nonce_proof' and returns 'ds_session_cookie_mock' on failure or when the upstream omits a token (src/plugins/deepseek.ts:285–311). High DeepSeek cooldown is a permanent state. Accounts are moved to status: 'cooldown', but getActiveAccounts() accepts only 'active' and this adapter never performs the expiry reset that Kilo, Nous and Cline implement (src/plugins/deepseek.ts:252–257, 542, 680). Once cooled down, a DeepSeek account is effectively dead until an operator intervenes.

Medium Developer path in shipped code. The OpenCode tool loader hardcodes C:\Users\adity\Videos\cline-proxy-main\… (src/plugins/opencode.ts:150). On any other machine the load fails silently and the plugin falls back to twelve embedded stub tool definitions. This is a portability defect, not a security one.

Medium Catalogue credibility. Model IDs such as nous/qwen/qwen4-max, kilo/particle-ai/particle-1:free, kilo/baidu/ernie-5.5-flash-preview:free, deepseek-v4.1-flash-free and claude-sonnet-4-5 are hand-maintained strings with a constant created: 1731693600. The project's own design document classifies such descriptors as declared and therefore unverified, which is the right epistemic stance; the problem is that combos route to them and the dashboard advertises them as if they were live. Live /v1/models synchronization exists in Kilo, Nous and FreeLLMAPI but is invoked only from probe() or listModels(), never from normal request routing (src/plugins/kilo.ts:1063, src/plugins/nous.ts:1044).

7.2 Extensibility assessment

Adding a provider currently requires touching at least four places: the new adapter file, both entrypoints (src/index.ts:23–47, bin/lattice.ts:59–83), the hardcoded prefix list in model-resolver.ts, and the static admin catalogue. There is no dynamic plugin discovery, no manifest format, no dependency declaration, and no isolation boundary — plugins are ordinary in-process classes with full filesystem and network access. Two resolvers implement different matching rules, and the combo resolver reaches into an untyped (plugin as any).cachedModels property that not every plugin has (src/utils/model-resolver.ts:60–68). The proxy pool is similarly incomplete: it is CRUD over in-memory state with no dispatch integration, and getNextProxy() increments its index before reading, skipping the first proxy (src/pool/proxy-pool.ts:38–45).

The honest conclusion: the plugin interface is a good execution seam and a poor ecosystem seam. Making it the latter requires catalog-driven resolution, a plugin manifest, and a single registry that both the router and combos consult.

08

Routing and virtual model combinations

Routing in Lattice is a two-stage process. The router maps a client-facing model string to a plugin; if that plugin is the combo engine, a second stage walks an ordered list of concrete models. Both stages are deterministic and static. There is no scoring function, no health input, no latency or cost objective, and no learning from outcomes.

8.1 Alias and provider resolution

A hardcoded alias table maps Claude Code and common short names onto two combos: most Sonnet/Opus variants go to lattice/code-flagship, Haiku variants and auto go to lattice/1m-free or lattice/fast-free (src/core/router.ts:157–174). This is pragmatic harness compatibility — it makes Claude Code work without configuration — but it collapses materially different models into one target. An Opus request and a Haiku request are not capability-equivalent, and a user who names a specific model may be silently served by an unrelated free one.

Resolution then checks a provider prefix, a plugin ID, and a 60-second catalog cache, with a single-plugin short circuit noted earlier. The catalog cache is not invalidated when admin APIs add or remove models, so changes can take up to a minute to become visible in routing. Separately, the combo engine's resolver uses hardcoded prefixes and scans plugins' cachedModels arrays rather than calling listModels(). These two algorithms can disagree about the same model string.

8.2 Combo execution

The combo engine is the most thoughtfully designed routing component. For each target in priority order it:

  • resolves the target to a plugin, skipping unresolved targets;
  • reads a context window from a signature-verified passport, falling back to the plugin descriptor and finally to substring heuristics such as modelId.includes('1m') → 1,048,576 tokens (src/plugins/combo.ts:62–111);
  • skips the target if the estimated prompt plus a 256-token safety margin leaves fewer than 256 output tokens;
  • skips the provider if all its accounts have zero remaining quota;
  • clamps maxTokens to the remaining window and executes the target;
  • on pre-content failure, rotates; on success, pins the target for the session.

Streaming failover adds an important refinement: the adapter pulls events until the first content-bearing one — text, thinking, tool start or tool delta — before returning the stream. A target that connects and then dies before producing content can therefore be retried without duplicating anything visible to the client. Once content has been emitted, a mid-stream failure produces a stream_error event rather than switching model, which is the correct trade-off for tool-calling agents (src/plugins/combo.ts:334–403). The target switch budget is four, so a ten-target combo will try at most four candidates.

Verdict on "intelligent routing"

The system is context-aware and quota-aware ordered failover, not intelligent routing. It does not choose among healthy providers by latency, price, quality or load; it does not use passport availability or measured latency; it has no circuit breaker or backoff; and its account selection is first-active rather than least-used. Calling it "intelligent" overstates what the code does. Calling it a well-engineered failover cascade does not.

09

Account, quota and credential management

The account model is richer than the routing built on top of it. A stored account carries status, cooldown timing and reason, error count, rate-limit reset, quota remaining/limit/reset, cumulative tokens and requests, and last-used time (src/core/types/plugin.ts:20–48). The pool implements cooldown expiry, reset-window detection, next-reset calculation, a four-hour long-cooldown rule that sets quota to zero, and invalidation after five errors.

Rotation policy is deliberately conservative and well reasoned. Kilo, Nous and Cline rotate an account on 401 (suspend) and 429 (cooldown plus Retry-After parsing, including natural-language forms in Cline), but fail fast on network errors, aborts and 5xx responses. The design rationale — an ambiguous failure may have processed a tool call or consumed a charge, so retrying another account could duplicate it — is correct and documented in the README. This is a good decision, even though it reduces availability.

The execution of that policy has three problems. First, selection is active[0] with a preference for a session-pinned ID; the round-robin method exists but is unused, so load concentrates on the first account. Second, there are no in-flight reservations or locks. Multiple concurrent requests can select the same account, and lastUsedAt is written at selection time then used later to attribute usage, so quota decrements can land on the wrong account (src/pool/account-pool.ts:360–373). Third, none of this runtime state is persisted: cooldowns, quota decrements and token counters are lost on restart, and globalStorage.save() is called only from a handful of admin mutations.

Credential handling is the strongest part of this subsystem. Imported accounts use opaque random IDs, store no secret in the account record, and resolve their credentials through globalCredentialResolver into the outbound header. The import flow requires an explicit operator-supplied path, returns only provider names, counts and a digest in preview, and binds a 60-second single-use confirmation token to the preview digest (src/core/account-import.ts:63–130). The secret store is honest about its backend: file storage is reported as file-fallback, and OS backends are advertised only after a real round-trip probe or tool presence check (src/core/secret-store.ts:189–230). Writes use a temp file plus atomic rename and mode 0600. External commands are invoked with execFileSync and argument arrays, with secrets passed on stdin — no shell interpolation.

Several adapters fabricate fallback numbers such as 10 prompt and 20 completion tokens when upstream usage is missing. The estimated honesty flag exists only in the internal log record, not in the response the client receives, so a downstream system cannot tell a measured count from a guess. The three conformance fixtures verify a handful of JSON dot-paths and substring presence; they do not assert event sequences, field-level stream payloads, error paths, real SDK compatibility, or any of the features listed as missing above.

11

Streaming and reliability analysis

The gateway has real reliability mechanisms: request deadlines, idle timeouts, keepalive comments, abort-signal plumbing, account rotation on unambiguous failures, and the pre-content buffering described above. It also has specific holes that matter under load or partial failure.

11.1 Timeouts and cancellation

High Deadlines do not abort upstream work. withRequestDeadline is a Promise.race between the work and a timer. When the timer wins, the caller receives a 504 but the underlying fetch keeps running; the client's abort signal is passed to the plugin separately and is not triggered by the deadline (src/utils/request-deadline.ts:4–16). Under sustained timeouts this leaks sockets, memory and provider quota. The streaming timeout wrapper emits a synthetic stream_error and cleans up its iterator, but likewise does not abort the upstream fetch.

Client cancellation is threaded correctly into execute and executeStream and through the interceptor and SSE adapters. The problem is accounting, not transport: on client abort the timeout wrapper returns without a stream_error, so the router's finally block still sees status 200, records usage and writes a successful log row for an incomplete stream (src/core/router.ts:348–371). This inflates quotas and telemetry precisely in the failure case.

11.2 Failure handling

There is no circuit breaker, no exponential backoff, no jitter, no bulkhead and no idempotency key. Retry loops try the next account or target immediately. A provider returning a uniform 5xx will be hit repeatedly on every request until exhausting the attempt budget, with no cool-down at the provider level. A client that retries an ambiguous failure may duplicate a tool call because nothing deduplicates requests.

The decision to fail fast on network errors, aborts and 5xx is defensible and documented; it trades availability for correctness. The inconsistency is that the combo engine's non-streaming path falls back on any error, including ambiguous ones, while individual adapters do not. The same request can therefore be retried at the combo layer after the plugin deliberately refused to retry at the account layer — the exact duplication risk the conservative policy was meant to avoid (src/plugins/combo.ts:214–226 versus src/plugins/kilo.ts:767–770).

11.3 Stream termination

Stream errors are in-band events on an HTTP 200 response. For OpenAI Chat the error chunk has no choices array and is followed by neither [DONE] nor a normal finish chunk; for Responses the failure is encoded as response.completed with status: 'failed' rather than a documented failure event. Keepalive comments are emitted on a 15-second interval, which prevents proxy idle timeouts but does not distinguish a healthy slow model from a stalled upstream — that distinction is made only by the separate 120-second idle wrapper.

Net assessment: the streaming architecture is sound and the pre-content rule is genuinely good engineering, but the error contract is weak. A gateway whose clients are coding agents needs the failure signal to be unambiguous, because an agent that cannot tell a truncated stream from a finished one will continue a conversation on a false premise.

12.1 What is done well

The browser-origin guard is a real control, not decoration: a loopback HTTP server is otherwise reachable from any page the operator visits, and a foreign Origin is rejected unless allowlisted (src/core/server.ts:67–78). Passport keys are generated locally, stored 0600, and signatures are verified on load with tamper and foreign-key tests. These are concrete, non-performative controls.

12.2 Boundaries that remain soft

Trust boundaries are concentrated at the admin API and the upstream URL field. An operator with the admin token can set arbitrary account base URLs (subject to the validator), trigger model probes that consume provider quota, write client configuration through the harness manager, and read redacted account metadata. The printed token in SEC-01 therefore deserves more weight than its "medium" label suggests.

There is also no rate limiting or brute-force protection on the token check, no audit log of admin mutations beyond the request ledger, and no separation between "read telemetry" and "mutate accounts" beyond the single admin token. For a single operator this is acceptable; it would not survive a multi-tenant deployment.

Persistence and data integrity

Persistence is the weakest major subsystem. The primary store, the ledger and the passport store use three different standards, and only two of them are defensible.

14.1 Primary store

data/lattice-store.json holds accounts, combos and proxies. save() calls writeFileSync directly on the live file with no temp file, rename, lock or debounce (src/pool/storage.ts:62–75). A crash mid-write can leave a truncated file. load() catches JSON parse errors, logs them, and continues with empty pools — so a corrupt file produces a running gateway with no accounts and no combos, and the next admin mutation overwrites the evidence (src/pool/storage.ts:32–60). There is no schema version, migration path, backup or quarantine. Plaintext credentials may be present in account records created through older paths; the import flow deliberately avoids this, but the model still permits it.

Runtime state is not persisted at all. Cooldowns, quota decrements, token counters, lastUsedAt, status transitions and rotation indices exist only in memory. A restart resets quota enforcement, which is both a correctness problem and an incentive problem for free-tier account use.

By contrast, the passport store, secret store and harness manager all use temp-file-plus-rename atomic writes, and the passport loader leaves a corrupt file untouched for operator recovery (src/core/model-passports.ts:208–241). The project knows how to do this correctly; the main store simply does not.

14.2 Ledger and passports

The NDJSON ledger tolerates a truncated trailing line on read but never repairs it, has no retention policy, and grows without bound. Its redaction-by-omission design is good: only numeric and routing fields are stored. Passports use a versioned schema, stable canonical JSON, SHA-256 digest, Ed25519 signature and verification on load, with measured claims protected from catalogue downgrades. The two known passport defects are the loss of availability during observe() and a strict > timestamp comparison that lets equal-time observations overwrite (src/core/model-passports.ts:250–263).

Data-loss windows

(1) Crash during a primary store write → whole-file corruption with silent fallback to empty state. (2) Any restart → all quota, cooldown and usage counters lost. (3) Corrupt ledger tail → one dropped record with no repair. (4) Client abort → a usage record is written for work that may not have completed. These are concrete, not hypothetical, consequences of the current code paths.

18.1 What the established projects do better

  1. Routing depth and measurement. OpenRouter routes on measured price, throughput, latency and reliability with percentile constraints [S11]; LiteLLM publishes several strategies with honest trade-off notes [S4]; Portkey exposes error-triggered fallbacks and weighted balancing in configuration [S9]. Lattice's static combo order plus 429/401/403 failover is correct but far less expressive.
  2. Multi-tenancy and organizational controls. LiteLLM, New API and Portkey document virtual keys, budgets, groups/RBAC and usage attribution. Lattice has one operator and one admin token.
  3. Protocol breadth. LiteLLM documents embeddings, images, audio, batches, rerank and A2A [S1]; New API adds Gemini and task plugins [S7]; Portkey adds realtime/WebSocket and MCP Gateway [S9]. Lattice covers three text dialects.
  4. Operational maturity. Shared cooldown state via Redis, managed database migrations, Helm/Terraform deployments, signed images and stable release channels [S1][S4]. Lattice uses local JSON files and in-memory affinity — appropriate for one machine, not HA.

18.2 What Lattice does differently

  • Consumer-grade upstream credentials as first-class plugins. Cookie sessions, keyless anonymous tiers and OAuth portal accounts. Most comparators assume clean provider API keys or subscription sign-in; New API's multiple upstream keys is the nearest analogue [S7].
  • Evidence-tagged capability records. None of the compared projects documents a declared/discovered/measured provenance model, nor an explicit statement that signing proves integrity rather than truth.
  • Idempotency-aware failover. Rotation is restricted to responses that prove the upstream did not process the request. OpenRouter triggers fallbacks on rate limits and downtime as well [S12]; Portkey's triggers are configurable but not framed around duplicate tool calls.
  • Privacy-minimizing affinity. Hash-only, in-memory, non-persisted, with no prompt storage — a stronger default than typical gateway request logs.
  • Local-first zero-ops UX. Single binary or Bun source, dashboard, and dialect coverage for Cursor/Claude Code/Roo-style clients without a Postgres/Redis footprint.

18.3 Ideas worth adopting

  • Declarative routing with weights, priority, affinity and error-specific fallback triggers — cite New API's channel model and Portkey's config semantics [S7][S9].
  • Local measured routing signals (success rate, latency, cost). OpenRouter's percentile constraints are a good conceptual model [S11]; heed LiteLLM's warning that usage-based routing adds Redis latency [S4].
  • A pluggable shared-state abstraction for cooldowns and quotas. OpenCode's manifest shape — env, package, settings, models — is a clean reference for Lattice's plugin metadata [S13].
  • Per-client keys and budgets, even for a single operator; IDEs and agents are distinct consumers.
  • A maintained dialect compatibility matrix tied to client releases. Claude Code's documentation is explicit that gateways failing to forward new capabilities break features [S16].

18.4 Approaches to avoid

  • Reusing AGPL-licensed source. New API is AGPL-3.0 [S8]. Borrow architecture, not code, unless the obligations are acceptable.
  • Unbounded failover on ambiguous errors. Broad fallback triggers combined with tool calls duplicate side effects. Lattice's narrow rule is the better default — keep it.
  • Flattening catalogue claims into facts. The passport evidence distinction is more defensible than aggressive capability normalization.
  • Persisting affinity or prompts. That would turn a routing optimization into a conversation store and undermine the privacy stance.
  • Assuming transparency is automatic. Third-party gateways are not endorsed or audited by Anthropic [S16]; every dialect layer needs a test matrix tied to client releases.
  • Secret-storage claims without probing. Lattice's “report the real backend, fall back to 0600” is the right pattern.

18.5 Where Lattice could credibly differentiate

Not on generic gateway breadth — LiteLLM, New API, Portkey and OpenRouter are far ahead on routing, tenancy, ecosystem and operations. The defensible position is the truthful local gateway for coding agents: messy consumer credentials handled with consent, evidence provenance presented honestly, failover classified by whether the upstream processed the request, and session continuity that stores no conversation. Those are structural properties, not marketing copy. They are worth protecting while the routing engine and protocol contract are rebuilt around them.

Missing capabilities

Separating "worth adding" from "feature bloat" matters here. The following gaps are grouped by whether they fix a real failure mode or merely add surface area.

19.1 Fix a real failure mode now

  • Atomic, versioned persistence with migrations and backup. Without it, every other reliability feature rests on a file that can be silently destroyed.
  • Upstream abortion and cancellation propagation. Deadlines must stop work, not just stop waiting.
  • A single routing decision engine that consumes account health, measured latency, quota and cost, with per-provider circuit breakers and backoff.
  • Protocol-correct streaming errors and Responses events. Client correctness depends on unambiguous termination.
  • In-flight account reservations and correct usage attribution. Required before any serious concurrency.
  • CI that runs verify and event-level conformance on every change. The project already has the checks; it does not enforce them.

19.2 Meaningful but later

  • Real per-model pricing and cost-aware selection. The data model exists; the price table does not. Useful only once usage numbers are trustworthy.
  • Policy-based routing — e.g. "prefer free, fall back to paid only after two failures" — expressed as data rather than hardcoded combos.
  • Model benchmarking and active capability probes with scheduling, budget controls and result history, building on the passport system.
  • Structured outputs, multimodal fidelity and cache-control passthrough where the canonical model can represent them without dialect-specific hacks.
  • Plugin manifests and dynamic discovery with declared capabilities, configuration schemas and lifecycle hooks.
  • Operational tooling: request replay from the ledger, trace export, per-provider SLOs, alerting on cooldown rates.

19.3 Deliberately out of scope

Multi-tenancy, distributed deployment, billing, a remote control plane, and per-message adaptive model selection would each add a new product rather than improve this one. The design document is right to name them as non-goals. A local gateway that is excellent at one operator's aggregation problem is more valuable than a mediocre attempt at a platform.

Recommended target architecture

The target is not a rewrite. It is the same system with four boundaries made explicit and four mechanisms made reliable.

20.1 Principles

  • One source of truth per decision. A single registry/catalog resolves models; a single routing engine chooses targets; a single account allocator owns selection.
  • Failures are typed and observable. Every upstream failure has a category, a retry decision, and an event visible to the client and operator.
  • State that matters survives restart. Accounts, combos and runtime quota state are versioned and written atomically.
  • Claims carry evidence. Extend the passport discipline to health, latency and pricing rather than treating static catalogue rows as facts.
  • Compatibility is executable. Protocol conformance is a test suite with event-level assertions, not a fixture that checks substrings.

20.2 Incremental changes (low risk, high return)

  1. Fix the Responses event names, tool-call IDs and stop-reason mapping; add event-level conformance assertions.
  2. Switch storage.save() to temp+rename, add a schema version, quarantine corrupt files and persist runtime quota state.
  3. Make deadlines abort upstream work; record usage only on confirmed completion.
  4. Replace first-active selection with an in-flight reservation and least-used policy; attribute usage by actual account ID.
  5. Consolidate the three router handlers into one dialect-parameterized pipeline and unify the two resolvers.
  6. Add a CI workflow running typecheck, dashboard guard, unit tests and conformance.

20.3 Architectural changes (higher cost, higher ceiling)

  1. A routing decision engine with an explicit policy pipeline: eligibility → capability fit → health → cost/latency → quota → selection, with reasons recorded for each decision.
  2. Provider manifests with declared capabilities, configuration schemas, lifecycle hooks and process-isolated execution for untrusted adapters.
  3. Extending passports from capability evidence into a general evidence store used by routing, benchmarking and pricing.
  4. Externalized state (a small embedded database or a durable key-value store) if multi-process deployment is ever wanted. Do not take this step without a multi-process requirement.

Final engineering verdict

Lattice Gateway is better built than its documentation suggests and less complete than its naming implies.

The canonical dialect layer, the pre-content failover rule, the evidence-first passport design and the refusal to fabricate telemetry are the work of engineers who think about failure modes. Those decisions are worth preserving. The gaps — non-atomic state, static routing, abort leaks, protocol-level streaming defects and absent CI — are equally real and mostly localized to boundaries that can be fixed without discarding the architecture.

The most valuable next step is not another provider or another dashboard view. It is making the existing decisions durable: atomic state, abortable requests, one resolver, correct stream events, and checks that run on every change. Do that, and the gateway's existing strengths stop being islands and start being a system.

Lattice Gateway

A gateway that pools five providers, speaks three dialects, and reports its own numbers. This audit tests the claims rather than the prose.

Sound core, edge debt

Verdict Unusually for a project this size, the core is not the problem. Atomic durable writes, a nonce-only CSP, an SSRF guard that blocks address aliasing, a loopback origin check without a loophole, twelve deterministic conformance fixtures, and a circuit breaker with correct single-flight probe semantics — all verified by hand. What is left is edge work: a gitignore pattern that would commit a token-bearing backup, a state file fsynced on every request, a ledger whose retention code nobody calls, and a suite that cannot tell a slow box from a regression.

03Critical

One finding. It is the only one that can put a live credential into a commit, and the fix is one character.

P0security

Versioned backups of the credential store are not git-ignored SEC-01

.gitignore lists data/lattice-store.json exactly, but the storage layer writes siblings with suffixes: .tmp on every save, .backup-<stamp> on schema migration, .corrupt-<stamp> on quarantine. None of those match the literal entry, so git sees them as new files.

This is already live. The tree contains a migration backup holding plaintext OAuth material, and git is ready to commit it:

git status: ?? data/lattice-store.json.backup-2026-11-24T12-54-03-765Z
Contents: 5 accounts · accessToken (JWT, 407 chars) · refreshToken (40 chars) · email
Check: git check-ignore data/lattice-store.json.tmp → not ignored
Source: src/pool/storage.ts:72 (backup), :64 (quarantine), :80 (writeAtomic .tmp)

FixIgnore the family, not the name: data/lattice-store.json*. Regenerate the suffix list from every ${filePath} template in storage.ts and secret-store.ts, then confirm with git status --untracked-files=all data showing nothing. If any of these files were ever committed on another branch, the tokens are burned and must be rotated at the provider — SECURITY.md already prescribes that order.

04High

These degrade reliability or trust in the numbers, and each is cheap to fix relative to its blast radius.

P1hygiene

Tests write into the operator's live telemetry SEC-02

Every other state file honours DATA_DIR, which is what lets tests and operators relocate the data directory. The ledger does not — it is constructed at module load from a hardcoded default:

src/admin/admin-router.ts:97
createLedger(process.env.LATTICE_LEDGER_PATH || 'data/request-ledger.ndjson')
DATA_DIR references in admin-router.ts: 0
Consequence: test traffic lands in the operator's real ledger — verified: one tier-4 run added 35 rows to data/request-ledger.ndjson

The test preload sets DATA_DIR to a temp directory, so the isolation looks complete but is not. Every test run permanently pollutes the numbers the dashboard reports, and because retention is never applied (OPS-01), the contamination cannot be aged out.

FixDefault to join(DATA_DIR || 'data', 'request-ledger.ndjson') so one option moves all state together. The test preload already sets DATA_DIR; this single change makes the ledger follow it.

P1ops

Ledger retention is implemented, documented, and never called OPS-01

The ledger has rotation on write (maybeRotate, size and age based) but pruning only runs inside prune() and rotate(), and nothing calls either. Rotation moves the file; it never deletes. The result is unbounded disk use and an unbounded set of files that rebuild() reads at startup.

Callers of .prune(): tests only (tests/unit/request-ledger-retention.test.ts:67)
Callers of .rotate(): none outside the module
On disk now: request-ledger.ndjson 7.9 MB + request-ledger.1795447239550-5uh4ck.ndjson 38.8 MB = 46.6 MB in 2 files
Defaults: retentionMs 7 days · maxFileBytes 10 MiB · rotateEveryMs 24 h

FixRun prune() on the same tick as rotation — after rotate() inside maybeRotate(), or on an hourly timer started once. Then delete rotation files older than retentionMs. Both are a few lines and turn three unused options into the policy the comments already describe.

P1perf

Startup reads and re-parses the entire ledger history synchronously OPS-02

rebuild() runs at construction and on every prune/rotate, reading each file in full, parsing every line, sorting by timestamp, and accumulating points. With 46.6 MB across two files that is a blocking startup cost, and it grows without limit because of OPS-01.

src/core/request-ledger.ts:203-230 readFileSync per file → parseLines → sort → addPoint loop
Measured at 1M rows: rebuild completed, queries then took 0.20 ms — the aggregation is fine, the load is the cost

FixAggregates are already O(1) per query. Stop rebuilding them from raw history: persist a compact checkpoint (per-hour buckets) next to the ledger and load that instead, replaying only files newer than the checkpoint. Combined with OPS-01 this bounds startup work to one retention window.

P1tests

Spawned-helper tests leak the real server process, and the leaked gateways poison later runs TEST-01

Several tests start a real gateway with spawn('bun', ['run', …]) and then kill('SIGKILL') it. On Windows that kills the cmd.exe shim, not the gateway. The listener survives, keeps the port, and every later run of the same test talks to the old process — whose store lives in a temp directory that no longer exists. That is why ADV-1 reports an invalid store: it is reading nothing, because the gateway it thinks it started never bound the port.

This is measurable and self-accumulating. After a single full-suite run:

Leaked listeners after one bun test: 3 bun processes still bound to loopback ports (45991, 50326, 50345)
Accumulated across this audit session: 48 orphaned bun listeners on loopback ports, oldest from 14:59
Spawn tree: spawn pid 29612 = cmd.exe /c bun run … → real server pid 32704 → after SIGKILL of 29612, pid 32704 still listening
Mechanism: spawn('bun', …) resolves to the npm bun.ps1/cmd.exe shim, which starts the real binary as a child
Verified fix: spawn(process.execPath, [entry]) → spawned pid is the listener; 3/3 ADV-1 rounds pass with a valid store and the port reclaimed each time

Two contributing factors make it worse. ADV-1 hardcodes port 45991 instead of an ephemeral port, so the second run collides with the first. And the exit path does not verify the child died, so the leak is silent.

FixThree lines. (1) Spawn the real binary, not the shim: spawn(process.execPath, [entrypoint], …). Verified — with that change the spawned pid is the listener, SIGKILL releases the port, and three consecutive ADV-1 rounds pass with a valid store every time. (2) Allocate an ephemeral port per test instead of hardcoding 45991. (3) Assert the port was released before the test ends, so a future leak fails loudly instead of silently poisoning the next run.

P1tests

Eleven of fifteen failures are the 5 s clock, not the code TEST-02

With the process table clean, the suite still fails 15 of 899, and 11 of those are "timed out after 5000ms". Four are real assertions. The distinction matters: the timeouts will not be fixed by touching the code under test.

Run 3 (clean process table): 884 pass · 15 fail · 491 s
11 timeouts: abort-storm 5084 ms, opencode-multiturn 6064, p1-1-characterization 11059, request-ledger-retention 60712, combo-failover 14683, multidialect-concurrency 12853 + 8926, proxy-rotation 7501, scenario-429-marathon 14516, long-horizon 5018, roo-cline-xml 6415
4 assertions: the cooldown wall-clock check, plus the three abort tests measuring setup latency

The timeout key under [test] in bunfig.toml is inert in Bun 1.4.2 — a control test that sleeps six seconds still fails at 5000 ms after raising the key to 20000. Only the --timeout CLI flag works, which means CI and local runs use different budgets unless the flag is written down.

FixPass an explicit budget as the third test argument (test(name, fn, 30000)) rather than relying on config, and put --timeout in the package.json script so CI cannot drift. Then re-run: what is left is the genuine assertion failures. Per PERF-01, expect several of the concurrency timeouts to disappear once the per-request fsync is gone.

P1honesty

The only priced model is one no plugin serves DATA-01

Pricing has a single entry, openai/gpt-4o. No enabled plugin exposes that exact ID — Kilo serves kilo/gpt-4o, which does not match, so the lookup returns null. In consequence every cost figure the dashboard shows is null, and the routing-cost ranking in the resolver is a no-op for every real candidate.

Probe: costUsd('openai/gpt-4o') → 0.00075 · costUsd('kilo/gpt-4o') → null · costUsd('gpt-4o') → null
src/core/pricing-data.json: 1 model, 12 lines
src/core/pricing.ts:72-82 rankRoutingCandidates returns input unchanged when any cost is null

This is honest by construction — costUsd refuses to invent numbers — but it means the cost column, the "saved" figures, and the price-aware routing are all inert. The README's cost claims are unbacked in practice.

FixEither populate pricing-data.json with the IDs plugins actually advertise, or drop the price column and the ranking until it does. A one-model table that matches nothing is worse than no table: it implies a capability that silently returns null.

P1perf

Every request fsyncs the whole state file before it can reply PERF-01

The account pool persists on each state change, and a state change happens on every completion — recordTokenUsage / recordProviderUsage call persistState() → save() → writeAtomic(), which writes, fsyncs, and renames the full store. That synchronous disk flush runs inside the response path.

Measured on this machine, one at a time:

save() alone: 214, 297, 324, 302, 314, 316, 302, 211, 523, 533 ms — median 314 ms for an 8 KB file
write+rename without fsync: 0.8 ms · with fsync: 84.5 ms
End-to-end, one non-streaming request: 825, 628, 431, 513, 417 ms
Same request with the persistence hook neutralised: 1, 1, 1, 1, 1, 1 ms
20 concurrent requests: 8,582 ms with persistence · 261 ms without

So the gateway's own latency is dominated by durability bookkeeping, not by the provider. The concurrency measurement makes the second-order effect concrete: 20 simultaneous requests take 8,582 ms with persistence on and 261 ms with it off — a 33× difference. Every concurrent-load test in the suite runs against that serialised fsync queue.

FixDebounce state persistence — coalesce writes on a short timer (the health store already accepts a debounceMs argument, so the pattern exists) and flush on shutdown and on state transitions that matter (account add, cooldown, combo change). Usage counters are the bulk of the churn and are reconstructible from the ledger; they do not need per-request fsync. This is the single change with the largest measured effect on the product: ~400 ms off a serial request and ~8.3 s off a burst of twenty.

05Moderate

Structural debt that slows every change, plus two findings where the code reports something it does not actually do.

P2structure

The plugin "manifest" system has exactly one user ARCH-01

There is a manifest type, a lifecycle registry, an adapter convention, and a JSON file — for one plugin. The other five are still hardcoded in two entrypoints, each of which repeats the same registration block. The abstraction costs more than the duplication it was meant to remove.

src/plugins/manifests/ 1 file (opencode.json)
src/plugins/adapters/ 1 file, 6 lines, constructs one class
src/index.ts:22-46 and bin/lattice.ts:58-82 — same hardcoded wiring, 50 shared lines
src/core/plugin-lifecycle.ts 42 lines, no hook declared by any manifest ("hooks": [])

FixPick a direction. Either migrate the remaining five (then delete the hardcoded blocks — the manifest path is genuinely better), or delete plugin-lifecycle.ts, the manifest types, and the adapter folder until a second plugin needs them. The current half-state gives you the cost of both designs.

P2duplication

Two entrypoints are 50 lines of copy, and one is already ahead of the other ARCH-02

src/index.ts and bin/lattice.ts both bootstrap storage, instantiate five plugins, load manifests, wire accounts, build config, serve, and install shutdown handlers. They have drifted: the banner, the port-conflict hint, and the storage path line differ.

Overlap: 50 of 131 bin lines appear verbatim in src/index.ts
Drift: src/index.ts says bun run src/index.ts --port; bin says lattice.exe --port; src prints a hardcoded "Active Plugins" list
Neither is built: bin/lattice.exe does not exist, yet both launchers prefer it when present

FixMake bin/lattice.ts a three-line wrapper that imports and calls a single startGateway() exported from src/index.ts. One banner, one hint, one place to add a plugin.

P2duplication

Five provider plugins are the same file with different constants ARCH-03

Kilo, Nous, Cline, OpenCode, and DeepSeek each implement execute, executeStream, listModels, healthCheck, probe, and classifyError with near-identical bodies. Kilo and Nous share 392 identical lines outright — hundreds of fourteen-line windows are byte-for-byte the same. Twenty-one call sites repeat the same new GatewayError(res.status, String(res.status), …) idiom.

Lines: kilo 1128 · nous 1098 · cline 942 · opencode 918 · deepseek 915
kilo↔nous: 392 shared lines · kilo↔cline 123 · nous↔deepseek 79
Error idiom: 21 occurrences of String(res.status) as an error code

FixExtract one BaseHttpPlugin holding the fetch/stream/error-mapping skeleton and let each provider override only URL building, headers, and response shape. That is the abstraction the manifest system promised and did not deliver. Also replace String(res.status) with a mapped code — a numeric string is not an error type.

P2correctness

Three dialect handlers repeat the same 150-line tail ARCH-04

Each of /v1/chat/completions, /v1/messages, and /v1/responses contains its own copy of prompt counting, gate, capability assertion, breaker recording, usage accounting, log broadcast, and stream-outcome bookkeeping — around 200 lines apiece. A fix to the accounting path must be made three times.

src/core/router.ts handlers at :162 (202 lines), :364 (201), :565 (150)
Repeated calls: gateProvider ×3 · assertProviderCapabilities ×3 · countPromptTokens ×3 · recordTokenUsage ×3 · recordProviderUsage ×3 · broadcastLog ×6

FixThe dialect-specific part is only normalize → resolve → serialize. Everything between is one pipeline: extract runDialect(handler) that takes a normalizer and a serializer. This is the single highest-leverage refactor in the codebase.

P2correctness

Request bodies are fully buffered before the size check can reject them ARCH-05

The body-limit middleware drains the stream into an array to count bytes, then rebuilds a Request. That is correct for chunked bodies with no declared length, but it means any such request — including a large legitimate prompt — is held entirely in memory before routing begins, and the reattached body is a fresh buffer rather than the original stream.

src/core/server.ts:81-112 reader.read() loop → Uint8Array concat → new Request
Trigger: declared === 0 — i.e. no Content-Length, which is the normal shape of a chunked upload

FixThe size ceiling is right; the cost is the copy. Stop reading at maxBytes (already done) and, where the dialect permits, stream-parse instead of concatenating. At minimum, document that this middleware defeats request streaming, since the project's own README advertises streaming as a core property.

P2honesty

The README documents a command that does not exist DOC-01

Section 10 tells the reader to run bun run why <request-id> to trace a request. There is no such script. buildReceipt exists and is tested, but nothing wires it to a CLI, so the receipt capability is unreachable from the documented interface.

package.json scripts: start, dev, test, test:unit, test:coverage, build, typecheck, check:dashboard, conformance, verify — no why
bun run why → error: Script not found "why"
src/core/receipt.ts exported, only called from tests/unit/receipt.test.ts

FixAdd the script (a 15-line file that reads the ledger, finds the ID, prints the receipt) or remove the paragraph. A documented interface that errors on use is worse than no interface.

P2hygiene

Token comparison is not constant-time SEC-03

The bearer check compares strings with !==. On a loopback-bound gateway this is a low practical risk, but the tokens are the only thing between the admin API and any local process, and the fix is one function.

src/core/server.ts:142 if (missingAdminToken || provided !== required)
timingSafeEqual uses in src: 0

FixCompare SHA-256 digests with crypto.timingSafeEqual. Hashing first also removes the length side-channel.

07What holds up

These were tested, not assumed. They are the reason the verdict is "sound core" rather than "rewrite".

PropertyHow it was verified
Atomic, durable storeThree rounds of SIGKILL two milliseconds into a 120k-account write: store parsed as valid every time, corrupt load quarantined and refused to start rather than silently resetting. This is the fix that most projects get wrong.
Dashboard injection defenceNonce-only CSP with no unsafe-inline, verified live: script-src 'nonce-…', object-src 'none', frame-ancestors 'none'. Adversarial test confirms a raw payload does not reach the grid unescaped.
SSRF guard on upstream URLsBlocks decimal/octal/hex IPv4 aliasing, IPv4-mapped IPv6, link-local 169.254, private ranges, and HTTPS→HTTP downgrade on redirect. Adversarial redirect to the metadata endpoint was refused with zero target hits.

Auth boundariesThe admin shell is public (it is static HTML); every admin data API returns 401 without the token, verified live. /v1/* requires the gateway token.
Dialect conformance12/12 fixtures pass across OpenAI Chat, Anthropic Messages, and OpenAI Responses, covering tools, thinking, SSE ordering, error frames, and client abort. Reproducible byte-for-byte.
Stream abort is immediateA direct probe shows abort surfacing in 0 ms with the upstream AbortController firing. Abort handling is genuinely correct; the slow abort tests measure per-request setup cost (PERF-01) and the harness shim (TEST-01), not a hang.
Circuit breaker semantics5xx/timeout/network count; 4xx and caller aborts do not; the half-open probe is single-flight and cancelled on ambiguous outcomes. Adversarial test: opens at threshold, blocks calls, then recovers.

09Method & reproducibility
